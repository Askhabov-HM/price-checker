# Миграции, версии расчётов и выпуск приложения

## Что хранится в каждой базе

`storage_meta` содержит магазин и формат совместимости. Существующие
`ozon_meta.version` и `lamoda_meta.version` остаются равны 1: их читают также
инструменты резервного копирования. Номер миграции не подменяет этот формат.

`storage_migrations` — журнал по компонентам: версия, SHA-256 определения,
время применения, релиз (`REVISION`, либо `workspace` при локальном запуске)
и происхождение. `legacy-baseline` означает регистрацию распознанной схемы
в момент перехода, а не выдуманную дату её исторического создания.
Схема и запись об успешной миграции фиксируются одной транзакцией.
Неизвестный магазин, неподдерживаемый формат, пропуск номера и изменение
контрольной суммы уже применённой миграции останавливают операцию.

Схемы основных таблиц, Telegram, диалогов Codex, Android, push и Windows
собраны в `src/storage-schema.js`. Производные таблицы и их триггеры также
регистрируются через общий механизм. Существующие ID, цены, даты, аккаунты,
очереди уведомлений и расписания не переносятся в другую базу.

## Правила следующих изменений

1. Опубликованную миграцию не редактировать. Добавлять следующую версию
   соответствующего компонента через `migrate()`, сохраняя старую функцию.
   Хеш нормализует окончания строк Windows/Linux.
2. Сначала распознать существующее хранилище; неизвестную схему не принимать
   автоматически за новую. Старые поддерживаемые формы Randewoo/Ozon
   нормализуются исходной миграцией без потери наблюдений.
3. При изменении таблицы сохранять необходимые индексы и триггеры. При
   перестройке таблиц проверять внешние ключи до фиксации транзакции.
4. Проверять чтение **и запись** предыдущим поддерживаемым релизом. Даже
   добавление колонки может сломать старый `INSERT ... VALUES` без списка
   полей. Несовместимое изменение требует нового `storage_meta.format`
   и соответствующего объявления в `storage-contract.json`.
5. Формат совместимости не повышать для каждого нового индекса. Нельзя
   обещать совместимость лишь потому, что SQLite открывает файл.

## Расчёты

`projection_versions` отделяет версии статистики (`rows`), общих графиков
(`history`) и опубликованных снимков (`published`) от схемы исходных цен.
При изменении формул увеличивать соответствующую версию в
`storage-contract.json`. Это явный контракт разработчика: произвольное
изменение JavaScript само по себе не анализируется на изменение смысла.

При несовпадении версии удаляются только соответствующие производные
результаты и строятся заново из истории. Это работает также при возврате
к прежней версии формулы. Проверка выполняется при чтении, включая уже
открытые соединения. Ошибка пересчёта откатывает и сброс кеша.
Версия опубликованного снимка зависит от всех трёх версий. Снимок текущего
незавершённого сбора нельзя пересобрать из частично записанных данных:
сначала сбор должен завершиться либо быть корректно отмечен прерванным.

Первый выпуск сохраняет существующие формулы v1 и принимает готовые кеши
как v1. Он не запускает запросы к магазинам для пересчёта. Структурные
изменения триггеров требуют миграции; одного увеличения версии формулы
для замены определения триггера недостаточно.

## Деплой

Установленный SSH entrypoint находится вне релиза:
`/usr/local/lib/price-checker/deploy.py`. До первого выпуска с новым
контрактом обновить его из проверенной сохранённой версии:

```sh
sudo bash scripts/setup-deploy.sh --update
```

Команда сохраняет предыдущий entrypoint, атомарно устанавливает новый,
не меняет SSH-ключ и не перезапускает приложение. Обычный CI-деплой сам
этот системный файл не заменяет. Обновлённый entrypoint отклоняет архивы
без `storage-contract.json` и инструмента подготовки баз.

Последовательность выпуска:

1. Проверить контракт нового релиза и форматы всех существующих баз.
2. Создать `.data/deployment.json`. Новые сборы перестают приниматься;
   расписания в базах остаются включёнными. Текущему сбору даётся до
   60 секунд, затем применяется обычная корректная остановка службы.
   При первом переходе старый код ещё не умеет этот протокол: используется
   его обычная обработка SIGTERM, без предварительного ожидания.
3. После остановки получить блокировки приложения, сборщиков Ozon/Lamoda
   и общей очереди. Создать проверенные SQLite-копии всех ожидаемых баз.
4. Под блокировками применить миграции и подготовить статистику и графики,
   включая архивные товары и отдельную историю Windows. Оставшиеся после
   аварии `running` отмечаются как `interrupted`; ожидающие Android-задания
   отменяются без изменения расписания и без сетевых запросов.
5. Запустить новый код с сохранённой технической паузой. HTTP readiness
   проверяет наличие сервисов, форматы и версии расчётов всех ожидаемых
   магазинов. Отсутствующее ожидаемое хранилище не создаётся молча заново.
6. После успешной проверки убрать паузу и через локальный защищённый
   control endpoint запустить Telegram и планировщики.

Подготовка SQLite выполняется в рабочем потоке. Главный поток процесса
блокировок продолжает обновлять heartbeat даже при длительном пересчёте.
Базы независимы: откат транзакции одной базы не отменяет уже выполненную
миграцию другой. Деплой оценивает фактические форматы всех баз.

`/api/health` возвращает 503 при недоступном ожидаемом хранилище. Ошибка
входа в магазин, HTTP 403 источника и отсутствие сети не являются ошибкой
готовности базы и не требуют отката релиза.

## Неудачный выпуск и откат

Перед запуском предыдущего кода проверяются его разрешённые форматы чтения
и записи. Если они подходят, подготовка выполняется инструментом именно
предыдущего релиза: он возвращает расчёты к своей версии. Актуальные базы
сохраняются, копии автоматически поверх них не восстанавливаются.

Для перехода с релиза без контракта разрешён только узкий случай:
структура всех таблиц, индексов и триггеров совпадает с копиями, сделанными
до текущего обновления, кроме новых таблиц учёта миграций/версий;
формат равен 1, расчёты остаются v1. Если добавились даже вспомогательные
таблицы, такой автоматический откат консервативно блокируется.

При несовместимости или неудачной проверке отката служба остаётся
остановленной, `deployment.json` получает фазу `blocked`, базы и копии
сохраняются. Новый деплой не перезаписывает незавершённый marker.
Нужен разбор причины и совместимое исправление; простое удаление marker
без проверки фактических баз не является восстановлением.

## Проверки

Регрессии покрывают атомарность миграции, повторное применение, контрольную
сумму, принятие старых баз, изоляцию магазинов, смену версии расчётов в обе
стороны, недопустимость публикации частичного снимка, подготовку таблиц
вспомогательных модулей, readiness и запрет несовместимого отката.
Проверки используют временные базы и подменённые системные службы;
e2e и реальные браузеры не требуются.
