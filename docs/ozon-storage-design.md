# Раздельное хранение Randewoo и Ozon

Дата: 17 октября 2026. Статус: проект. Дополнение к [общему проекту Ozon](ozon-design.md).

## Решение и обязательные границы

Две физически независимые базы магазинов. Требование пользователя заменяет первоначальное предложение одной SQLite с признаком источника.

- Нынешний `prices.sqlite3` содержит исключительно данные Randewoo; его путь в первой поставке сохраняется.
- `ozon/prices.sqlite3` содержит исключительно данные Ozon.
- Каждая база владеет своими товарами, вариантами, списками, наблюдениями, заданиями, расписанием и результатами синхронизации.
- Каждый магазин имеет собственные миграции, версию схемы, backup, восстановление и очистку.
- Общие интерфейсные компоненты и алгоритмы не требуют одинаковой схемы таблиц.
- Нет общего каталога товаров, общей таблицы наблюдений, межбазовых внешних ключей, SQL JOIN или ATTACH между магазинами.
- Выключение Ozon не требует открытия его БД, а удаление данных Ozon не затрагивает Randewoo.

Одна кодовая база и один веб-интерфейс сохраняются. Разделение БД не требует отдельного репозитория или второго сайта.

## Каталоги и владельцы данных

Структура первой поставки сохраняет путь существующей БД Randewoo. Его назначение задаётся явной конфигурацией и метаданными, а не общим именем `prices`:

```text
.data/
  prices.sqlite3         только Randewoo, существующая база
  backups/               только копии Randewoo
  imports/               только прежние импорты Randewoo
  ozon/
    prices.sqlite3
    backups/
  app/
    state.sqlite3
    backups/
  server.log
  server-error.log
```

Служебные файлы SQLite относятся к той же базе и лежат рядом с ней. Сессии магазина хранятся вне Git в отдельных приватных каталогах; серверный браузерный профиль Ozon также приватный. Существующий файл входа в Price Checker можно сохранить по прежнему пути `.secrets/price-checker-auth.json`.

На Ubuntu корень данных остаётся `/var/lib/price-checker/data`, как в текущем деплое; новые каталоги `ozon` и `app` находятся внутри него. Релизы содержат код, а данные переживают переключение релиза. Для worktree и экспериментов нужен собственный корень данных, без ссылок на рабочие базы. Симметричный каталог `randewoo/prices.sqlite3` можно ввести позже отдельной операцией с собственным backup и проверкой; перенос существующего файла не входит в обязательные работы для Ozon.

| Хранилище | Что в нём хранится | Кто пишет |
| --- | --- | --- |
| Randewoo SQLite | Существующие товары, пробники, цены, списки, проверки, настройки, отчёты Randewoo | Только сервис Randewoo |
| Ozon SQLite | Товары любых категорий, предложения, контексты, цены, снимки списков и события Ozon | Только сервис Ozon |
| Служебная SQLite приложения | Cursor входящих обновлений Telegram, общие диалоги, служебные статусы обработки команд | Сервис приложения и один обработчик Telegram |
| Приватные сессии Randewoo / Ozon | Данные подключения соответствующего магазина | Только код подключения и транспорт соответствующего источника |

Служебная база не получает таблицы или выгрузки товаров, цен, списков и их истории. Пользовательская переписка хранится как переписка; она не является источником товарной истории. Общие параметры входа в приложение не переносятся в базы магазинов.

Текущий Telegram использует БД Tracker для входящего cursor, исходящих отчётов и диалогов. При разделении один poller читает обновления для одного бота, затем направляет команду в выбранный сервис. Очередь отчётов о проверках и cursor обработки проверок остаются в базе соответствующего магазина; глобальный cursor Telegram и общие диалоги переезжают в служебную БД. Два независимых poller для одного токена не проектируем. Это причина отдельного служебного хранилища, а не третья база цен.

## Границы кода и API

Предлагаемое устройство:

```text
src/
  app/                  реестр сервисов, HTTP, вход, служебное состояние
  providers/
    randewoo/           service, client, storage, migrations
    ozon/               service, client/worker, storage, migrations
  shared/               алгоритмы и типы результатов без выбора БД
```

Каждый сервис получает своё хранилище при создании. В обработчиках Ozon нет доступа к универсальному `tracker.db` и нет fallback на БД Randewoo. HTTP выбирает уже созданный сервис из фиксированного реестра по разрешённому имени источника; путь к файлу никогда не приходит из запроса. Браузерный worker Ozon возвращает данные сервису Ozon, который записывает их в его базу.

Одна таблица может иметь локальный `id=42` в обеих базах — это нормально. Для новых API публичные ссылки на сущности включают источник и тип: `ozon:item:42`, `randewoo:item:42`, `ozon:context:7`. Маршрут проверяет префикс до обращения к хранилищу. Объект другого источника отклоняется; приложение не ищет его во второй базе. Публичные ID сериализуются на границе API, внутренние числовые ключи остаются локальными. Старые API с числовыми ID продолжают обращаться только к Randewoo.

Ключи кеша и сохранённых UI-настроек включают магазин. При переключении не показываются прежний список, открытый товар или сохранённый контекст другого магазина. CSV-экспорт относится к одному выбранному магазину и указывает его в имени файла/метаданных. Межмагазинный сводный экран не входит в первую версию.

## Защита от ошибочного выбора базы

При открытии ожидаются одновременно правильный каталог и метаданные внутри файла: `provider=randewoo` или `provider=ozon`, плюс версия схемы. Служебный файл имеет отдельный тип `app`. До любых доменных миграций проверяется тип файла; неизвестную непустую БД нельзя автоматически переобозначить или инициализировать как новую.

При запуске проверяются абсолютные канонические пути: два сервиса не должны указывать на один файл через разные симлинки или конфигурационные имена. Существующая БД без метаданных принимается только явной процедурой перехода Randewoo с проверкой известной схемы. Отсутствие ожидаемой рабочей БД при восстановлении — ошибка, а не разрешение создать пустую замену. Создание новой БД допускается отдельным сценарием первого подключения источника.

Версии схем независимы: версия Ozon не сравнивается с версией Randewoo. Миграции принадлежат модулю магазина и не перебирают все SQLite в каталоге. Общий код подключения не создаёт таблиц Randewoo в пустой базе Ozon.

Раздельные файлы устраняют общие таблицы и блокировки записи между магазинами. При этом общий сервер приложения и релиз остаются общими: его штатный перезапуск кратко затронет оба раздела. Ошибка подключения/чтения/миграции одного источника должна переводить в ошибку этот источник, сохраняя доступ к другому. Браузерный процесс Ozon имеет отдельные лимиты ресурсов.

## Переход от текущего хранения

Нынешняя `.data/prices.sqlite3` — база Randewoo. Переносить её данные в Ozon или преобразовывать доменную схему ради Ozon не нужно.

1. Подготовить манифест перехода с действующим путём БД Randewoo, версиями схем и точками восстановления. Остановить все записи приложения, Telegram и сборщиков на время переноса общего состояния.
2. Получить согласованную резервную копию штатным SQLite backup-механизмом. Не копировать только основной файл работающей WAL-базы. Сохранить исходник и backup до принятия результата перехода.
3. Оставить активную базу Randewoo по существующему пути. Зафиксировать контрольные значения ключевых таблиц, ID, цены, временные метки, членство и настройки; добавить метаданные принадлежности после проверки известной схемы. Не перенумеровывать сущности и не переписывать историю.
4. Перенести глобальные служебные данные Telegram и диалогов в `app/state.sqlite3`, сохранив ID, cursor и статусы доставки. Исходящие отчёты Randewoo остаются в Randewoo. Сверить перенос и доменные контрольные значения; удалить неиспользуемые глобальные служебные таблицы из активной базы Randewoo только миграцией после проверки. Исходный backup остаётся целым.
5. Отдельно создать пустую БД Ozon по собственной схеме. На этапе эксперимента она находится в отдельном временном корне и не подменяет рабочую БД.
6. Дополнить конфигурацию путей и backup/deploy новыми хранилищами, сохранив действующие путь БД, импорты, флаг однократности и приватный путь сессии Randewoo.
7. Запустить приложение и проверить старые маршруты/историю Randewoo, служебное состояние и новый источник. Перенос повторяем безопасно: завершённый манифест не позволяет ещё раз импортировать старые данные или повторно отправить очередь.

До возобновления обработки Telegram rollback возвращает старый релиз с проверенным исходным снимком и прежними путями. После появления новых записей возврат к старому снимку может потерять историю/повторить доставку: сначала остановить обработчики, сохранить актуальные базы и применить заранее проверенный обратный перенос служебного состояния или исправление вперёд. Простое переключение старого кода после выноса служебного состояния не является достаточным rollback. Это отличается от текущего деплоя, где совместимость единственной базы предполагалась.

## Backup, восстановление, очистка и деплой

| Операция | Граница действия |
| --- | --- |
| Backup Ozon | Только его SQLite и манифест `provider=ozon`; сессия не включается в обычный backup цен |
| Восстановление Ozon | Остановить задания Ozon, закрыть его соединение, проверить тип/схему/целостность копии, восстановить только Ozon и переоткрыть сервис |
| Очистка Ozon | Явно выбранный источник; только его доменные данные, без Randewoo и общих диалогов |
| Миграция Ozon | Только его каталог, БД и собственная версия схемы |
| Выпуск приложения | Согласованные backup всех существующих баз по поимённому манифесту до запуска миграций |

Файлы backup лежат в отдельном каталоге своего магазина: существующий `.data/backups/` закреплён за Randewoo, `.data/ozon/backups/` — за Ozon. Новые имена содержат магазин, время и версию схемы. У копии есть машинно проверяемые метаданные владельца; имя файла само по себе не считается достаточным. Старые копии Randewoo без метаданных требуют проверки известной схемы через отдельный режим совместимости. Восстановление копии Ozon как Randewoo отклоняется.

Для копии работающей базы использовать существующий SQLite backup-подход. Поскольку между магазинами нет общих транзакций, для обычного независимого backup не нужен единый момент времени двух баз. Для перехода служебных данных и перед миграциями релиза обработчики останавливаются, затем создаётся полный комплект копий с манифестом.

Текущий `scripts/deploy.py` делает backup только `/var/lib/price-checker/data/prices.sqlite3`; его нужно обновить до включения новых путей. Политика отката кода обязана учитывать схемы и расположение всех существующих баз. Если версия схемы несовместима со старым кодом, автоматический rollback не должен открывать эту базу старым сервисом и не должен молча восстанавливать устаревшую копию с потерей новых наблюдений.

Общий health сообщает доступность веб-приложения, статусы магазинов проверяются отдельно. Необязательный ещё не подключённый Ozon не ломает проверку работоспособности Randewoo. Готовность релиза оценивается по заранее выбранным включённым источникам и версии служебного хранилища; ошибки миграций не маскируются успешным ответом общего health.

## Наблюдение при смене продавца

Подтверждено пользователем: наблюдение за товаром продолжается, событие смены продавца видно в интерфейсе. Из аккаунта читается обычное избранное; именованные вишлисты не требуются.

Доставка для наблюдений — Грозный, выбранный адрес/пункт выдачи из аккаунта. В истории Ozon сохраняются город и ссылка на контекст без полного адреса. Чтение адреса не затрагивает базу Randewoo или служебные диалоги приложения. Неподтверждённый регион не подменяется Грозным, смена выбранного адреса создаёт новый контекст.

В Ozon разделяем стабильную цель наблюдения (конкретный товар и вариант) и предложения продавцов. Технический эксперимент должен определить, какие внешние ID и связи действительно позволяют подтвердить тот же товар/вариант. Совпадение названия или смена URL сами по себе недостаточны.

| Проверка | Наблюдение | Отображение |
| --- | --- | --- |
| 10:00 | Продавец А, 1 200 ₽ по карте | Обычная точка истории предложения А |
| 14:00 | Продавец Б, 1 050 ₽ по карте, тот же подтверждённый вариант | Та же цель наблюдения; событие «А → Б», новая цена и разница −150 ₽ с пометкой смены продавца |
| 20:00 | Продавец Б, 1 000 ₽ по карте | Снижение −50 ₽ внутри предложения Б |
| Следующая | Продавец неизвестен или карточка не прочитана | Не создавать ложную смену; сохранить цену и продавца последнего успешного наблюдения с временем и статусом ошибки |

На графике товара остаётся вся история с разделением по предложениям и отметками смены. У отметки — старый/новый продавец, обе известные цены и время обнаружения. Время фактической смены между проверками неизвестно: показывается «обнаружено при проверке». Переименование магазина при том же стабильном ID продавца не равно смене продавца.

События смены и цены сохраняются раздельно. Разница при переходе к другому продавцу видна пользователю, но не называется скидкой у старого продавца. Статистика изменения внутри предложения, минимум у продавца и минимум по товару среди наблюдавшихся предложений подписываются явно. Две цены (обычная и Ozon Карта) имеют отдельные ряды и отдельную доступность; нельзя вычислять разницу между разными типами цены.

Если исходное предложение недоступно, но источник явно даёт связанное актуальное предложение того же варианта, продолжаем с ним и фиксируем событие. Если подтверждённой замены нет, цель остаётся активной, показывает «нет доступного предложения» либо результат ошибки и проверяется по расписанию дальше. Не переходим автоматически к другому размеру, цвету, объёму или комплектности. Автоматический поиск минимальной цены по всем продавцам и подбор аналогов не входят в этот сценарий.

Корзина аккаунта остаётся отражением фактических строк Ozon: приложение её не редактирует и не меняет продавца в ней. В наблюдении можно продолжать следить за актуальным предложением карточки отдельно от состава корзины. Сопоставление исчезнувшей и новой строки корзины требует подтверждённого варианта; иначе это два изменения состава, а не доказанная смена продавца.

Публичной достоверной статистики частоты смены продавца в исследовании не найдено. Нельзя заранее обещать частые или редкие события. Собственная статистика будет считать долю целей со сменами и число обнаруженных переходов за период при известном числе успешных проверок; она отражает только наблюдаемую выборку и может пропускать переходы между проверками.

## Критерии приёмки при реализации

1. Добавление товара, проверка, изменение расписания и удаление Ozon не меняют доменные таблицы Randewoo. В тесте служба Randewoo остановлена, логические строки сравниваются до/после.
2. Миграция, backup и восстановление Ozon не открывают Randewoo для записи. Ошибочная передача файла или префикса ID отклоняется до доменных SQL.
3. Одни локальные ID в обеих базах не смешивают детали товара, кеш, CSV и операции изменения списков.
4. Два источника не могут получить один канонический файл БД; неизвестная непустая база не переинициализируется как Ozon.
5. Перенос текущей БД сохраняет доменную историю Randewoo и служебные cursor/очереди без повторной обработки команд.
6. Повреждение/блокировка/неприменимая миграция Ozon дают ошибку Ozon; Randewoo остаётся доступен. Независимое восстановление не сбрасывает другую базу или общие диалоги.
7. Подтверждённая смена продавца сохраняет ID цели, предыдущие наблюдения и отдельное событие; неизвестный продавец не создаёт событие. Отличающийся вариант не принимается автоматически.
8. Новый способ получения Ozon подтверждён на текущем сервере: корзина, обычное избранное, приоритетная карточная цена, получение выбранного адреса в Грозном, перезапуск с сохранением контекста и переподключение сессии. Данные неподтверждённого региона не записываются как цены для Грозного.

Документ задаёт будущую доменную схему. В первом эксперименте создана только собственная `.data/ozon/probe.sqlite3` для диагностики доступа; история цен Ozon и служебное хранилище приложения ещё не создавались. База Randewoo не переносилась и не изменялась. Ответы Network и сессия хранятся приватно вне SQLite и Git. Тест сравнивает файл Randewoo до и после работы диагностического хранилища Ozon.
