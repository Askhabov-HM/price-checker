# Ozon: результаты первого эксперимента

17 октября 2026. Ветка `design/ozon-support`, отдельный worktree `price-checker-ozon-design`.

## Результат

Последующее обновление 18 октября: реализован `/ozon` с отдельной БД цен и выключенным по умолчанию расписанием. Повтор одного HTTP-чтения в 15:04 МСК получил 403, а та же карточка в сохранённом серверном Chrome — JSON 200 с подтверждёнными аккаунтом, доставкой, обеими ценами и продавцом. Ошибка и успешная браузерная проверка сохранены раздельно. Долговечность HTTP-доступа без браузера этим не подтверждена. См. [реализацию и новую проверку](ozon-ui.md).

Обновление 18 октября: в новом профиле Chrome непосредственно на Linux VDS публичная карточка вернула JSON 200 и затем HTML 200. После самостоятельного входа владельца через удалённое окно получены JSON 200 избранного, корзины, одной карточки и её списка банков; подтверждены тот же аккаунт/доставка, последние 30 избранных, обе цены и продавец. Немедленный перезапуск сохранил вход, доставку и порядок тех же 30 SKU. Пик памяти с удалённым окном около 590 МиБ, без OOM и swap. Полный протокол — [публичная карточка и вход на Linux](ozon-public-product-linux.md).

Следующий ручной тест новой Linux-сессии в Node HTTP прошёл при закрытом Chrome: избранное, корзина, одна карточка и её банки вернули JSON 200, всего четыре GET без перенаправлений. Подтверждены аккаунт/доставка, 30 избранных, 3 строки корзины, обе цены и продавец; HTTP-сессия восстановилась новым процессом. Пик RSS Node около 113 МиБ. Постоянный worker, рабочий импорт cookies и двухчасовые циклы ещё не реализованы; прежняя диагностическая пауза сохранена. Подробности — [HTTP после Linux-входа](ozon-http-linux-session.md). Ниже сохранена история предыдущих опытов.

Через Chrome DevTools MCP получены настоящие ответы Network авторизованного локального Chrome. Реализован их разбор: последние 30 настоящих избранных, 3 позиции корзины с количеством, обе цены одной доступной карточки и числовой ID продавца. Снимок проверяется повторно без сети.

Ранняя авторизованная попытка HTTP с VDS 17 октября, 19:32 UTC (22:32 МСК) получила 307 → 403. Клиент обновил сессию, выполнил один проверенный переход и остановился. С той сессией избранное, аккаунт и доставка не подтвердились; расписание не включалось. Последующий успех новой Linux-сессии описан выше.

Локально рабочее чтение через Node подтверждено: обновление выданной cookie и один переход привели к JSON 200 с теми же последними 30 избранными, что и в Chrome. Причина различия локального и серверного результата пока не установлена. Из 403 нельзя заключить, что заблокирован аккаунт, или что браузер обязательно решит проблему.

Дополнительная проверка обычного серверного Chrome с новым профилем также получила 403 на главной странице, до входа в аккаунт. Ozon показал предложение выключить VPN или сменить сеть. Локальные cookies в этот браузер не переносились; профиль, процессы и данные изолированы от Randewoo. Проверка маршрутов позже подтвердила, что эти обращения шли напрямую с VDS, а не через локальный Mihomo. Российская классификация IP сторонними геобазами не доказывает такую же оценку со стороны Ozon.

Последующий контроль браузерного окружения дал другой результат: новый Windows Chrome через SOCKS-туннель с выходным IP того же VDS прошёл автоматическую проверку и открыл публичную главную с 200. Исходный Linux Chrome остался на 403. Это опровергает предположение о безусловном отказе для всех обращений с IP VDS, но не выделяет конкретную причину среди окружения и состояния профиля. В обоих контрольных профилях вход в аккаунт не выполнялся. Перенос выданной Windows-браузеру проверочной cookie в серверный HTTP-клиент с ранее сохранёнными cookies аккаунта не помог: один GET избранного 20:24 UTC снова вернул 403. Подробности — в [сравнении окружений](ozon-browser-environment.md).

Затем владелец вошёл в отдельный Windows-профиль с выходом через тот же VDS. Четыре явных GET из браузера вернули JSON 200: избранное, корзина, одна карточка и её список банков. Подтверждены совпадение аккаунта и доставки, последние 30 настоящих избранных, 3 позиции корзины, обычная и проверенная цена Ozon Карты, числовой ID продавца одной карточки. Браузер по-прежнему работал на компьютере владельца; автономная работа непосредственно на Linux VDS не подтверждена. Подробности — в [аккаунтной проверке](ozon-account-browser-check.md).

Ограниченный повтор на Linux VDS с `ru-RU`, работающим WebGL/WebGL2 через SwiftShader и 10 cookies сохранённого Windows-аккаунта получил 403 на избранном. Отправка cookies доступа/аккаунта подтверждена в Network; принятие входа не подтверждено. Переход на выданный Ozon `/challenge.html` завершился `/abt/challenge/fail`, HTTP 403. Наибольший зафиксированный пик Chrome с Xvfb — около 427 МиБ при лимите 768 МиБ, без OOM и swap. Полный сбор товаров не был достигнут. См. [ограниченный Linux-тест](ozon-linux-browser-check.md).

У первого ответа 307 не сохранены `Location` и признаки назначения, поэтому точно разобрать его задним числом нельзя. Диагностика дополнена безопасными признаками наличия/корректности `Location`, совпадения origin/пути и изменения query; сами URL и значения параметров в SQLite и публичный вывод не записываются. Учитывается `Retry-After` также для перенаправлений. Двухчасовая пауза первого запроса установлена нашим кодом; `retry_after_ms` у того ответа был равен 0, Ozon не задавал этот срок.

### Контрольная проверка перенаправления

Владелец явно запросил проверить HTTP-перенаправление до серверного браузера. Выполнен отдельный ручной эксперимент из двух GET; обычное расписание и его пауза не снимались:

1. 17 октября 2026, 19:14 UTC: исходный GET избранного вернул 307. `Location` сохранил HTTPS origin, путь API и исходный параметр `url`, добавив `__rr=1`. Ответ выдал новую `__Secure-ETC` со scope `Domain=.ozon.ru; Path=/; Secure; HttpOnly`. Тело — стандартная HTML-страница 307 без скриптов. `Retry-After` отсутствовал.
2. 19:15 UTC: один переход по выданному `Location` с обновлённой `__Secure-ETC` вернул `200 application/json;charset=UTF-8`, около 294 КБ. Дополнительных перенаправлений и автоматических повторов не выполнялось.
3. Парсер подтвердил сортировку «Новые», 30 настоящих избранных и совпадение их SKU/порядка с ранее полученным снимком Chrome. Рабочая история цен не изменялась.

Полные заголовки, новые cookies и ответы сохранены только в приватном каталоге `.secrets/ozon-redirect-*`. Точное назначение `__Secure-ETC` не установлено; опыт показывает, что для этого запроса достаточно перехода с обновлённой cookie. Это не доказывает стабильность всех будущих проверок или доступность с серверного IP.

Поведение перенесено в основной `requestOzonJson`. Он принимает только полученное от сервера перенаправление на тот же HTTPS origin и API, с неизменным `url` и единственным известным параметром `__rr=1` либо `2`. Максимум два перехода, один общий timeout; повторного запроса после 401/403/429 или challenge нет. `Retry-After` останавливает немедленный переход.

Сессия обновляется через `tough-cookie` с проверкой domain/path/secure-префиксов. Исходный Cookie из Network не содержит метаданных срока и scope: он используется только для исходного API. Полученная cookie заменяет исходную по имени, включая явное удаление, и сохраняется атомарно с режимом 0600. `Max-Age` превращается в абсолютный срок, который чтение не продлевает. Перезапуск не возвращает удалённую cookie. Никаких гарантий срока жизни исходной авторизации это не даёт.

Добавлены тесты перенаправлений, петель, посторонних origin, подмены страницы, удаления/истечения cookies и восстановления сессии. До запроса в БД фиксируется начало попытки: аварийное завершение оставляет паузу. Временные ошибки увеличивают ожидание до остановки на третьей подряд; первая 429 ждёт минимум шесть часов либо дольше по `Retry-After`, повторная требует проверки владельцем.

### Проверка с VDS

В отдельном `/var/tmp/price-checker-ozon-http`, от непривилегированного пользователя службы, выполнено одно логическое чтение избранного с приватной копией сессии. Фактических GET два: исходный запрос и переход. Результат — HTTP 403, `Retry-After` отсутствует; корзина, карточки и список банков после этого не запрашивались. Запросы остановлены без смены IP, повторов и альтернативного обхода.

Ответ 403 внесён в отдельную `.data/ozon/probe.sqlite3` этого эксперимента без повторного обращения к Ozon. Состояние `action_required=true`, `reason=access_limited` сохраняется после запуска нового процесса и после истечения обычного интервала. Минимальный `not_before` — 21:32 UTC; его наступление само по себе не снимает остановку. Команда `ozon:server-check -- --once` при паузе делает ноль запросов. Timer/worker не установлен. Продакшен `price-checker.service` остался активен.

`account-context.js` сравнивает ID аккаунта и отпечаток выбранной местности/видимого адреса с приватным эталоном из Chrome. Для стартового избранного нужен явный `isLoggedIn=true`. Публичный отчёт содержит только флаги совпадения и полноту списка. На сохранённых настоящих данных проверены тот же аккаунт/доставка и 30 избранных; серверный 403 не позволяет выполнить эти проверки там.

Проверки кода: `npm run check` и `npm test` прошли — сборка, 159 backend-тестов и 25 frontend-тестов. Среди них восстановление сессии/паузы, остановка после ошибок, проверка аккаунта и доставки и независимость базы Randewoo. Эти проверки не заменяют продолжительного живого испытания.

Браузерный путь чтения на VDS подтверждён 18 октября. Следующий этап — ограниченный worker и эксплуатационная проверка; масштабная переработка Randewoo, перенос служебных таблиц и новый интерфейс Ozon ещё не выполнялись. Текущая продакшен-служба не менялась.

## Фактический источник данных

Для чтения подтверждён GET `/api/entrypoint-api.bx/page/json/v2` с параметром `url`, указывающим на `/cart`, `/my/favorites?sorting=last_added`, `/product/<SKU>/` либо возвращённый виджетом цены `/modal/pdpListOfBanks?product_id=<SKU>`. Диагностический клиент принимает только этот endpoint и эти контексты, не отправляет POST и не делает автоматических повторов. Для аккаунтного JSON допускается только описанная выше ограниченная форма перенаправления. Ссылка банков сверяется с SKU исходной карточки и не может содержать другие параметры.

`widgetStates` содержит JSON-строки виджетов. Суффиксы идентификаторов зависят от страницы и выдачи, поэтому конкретные числа в них не используются как константы.

- Избранное: `tileGridDesktop`, `favoriteProductMoleculeV2.isFav`, `sku`, текст с `id=name`. Включаются только виджеты контейнера `default`; отдельная выдача `recoms_pagination_favorites_web` исключена, даже если предложенный товар уже присутствует в избранном.
- Порядок: выбранная сортировка проверяется по `searchResultsSort`; продолжение читается из `infiniteVirtualPaginator`. Обычный `paginator` на той же странице ведёт к рекомендациям и не подходит для синхронизации списка.
- Размер страницы не фиксирован: наблюдались блоки по 8 плиток с аналогами и ответ с 36 настоящими избранными. Нельзя рассчитывать последние 30 по числу плиток или смешивать курсоры разных ответов.
- Корзина: `cartSplit.cartItems`, точный `product.id`, количество, вариант и `priceColumn`; полнота сверяется с `master.summary`. В `summary` количество приходит строкой.
- Карточка: `webDetailSKU.copyText` подтверждает ожидаемый SKU, `webProductHeading` даёт название, `webPrice` — наличие и цены. Другой SKU отклоняется.
- Продавец: числовой ID доступен в параметрах элементов подписки внутри `webCurrentSeller`; элементы только читаются. Имя магазина само по себе не является идентификатором.

Надпись «С банками» и имя поля `cardPrice` недостаточны для подписи «Ozon Карта». В эксперименте прочитан указанный карточкой `/modal/pdpListOfBanks` для того же SKU; среди банков указан Ozon Банк. Без такого подтверждения либо явной надписи Ozon Карты парсер возвращает банковскую цену отдельно, а `ozon_card_kopecks=null`. Старая перечёркнутая цена сохраняется отдельно от обычной. Отсутствующая цена остаётся `null`.

Все денежные значения нормализуются в целые копейки; учитываются узкие и неразрывные пробелы. При неизвестной структуре ответ отклоняется. Незавершённая выборка избранного имеет `complete=false` и не является основанием для удаления ранее сохранённых позиций.

## Изоляция и воспроизведение

Приватные ответы, запросы с сессией и манифест лежат в игнорируемой `.secrets/` этого worktree. Полный адрес, Cookie, аккаунтные поля, сырые ответы, полные `Location` контрольного эксперимента и настоящий список избранных не включаются в Git или тестовые fixtures. Для согласованной проверки на сервер передана отдельная приватная копия запросов/сессии и эталон аккаунта/доставки; корень эксперимента доступен только владельцу, новые session-файлы имеют режим 0600. В продакшен-каталоги данные не переносились.

Диагностика использует только `.data/ozon/probe.sqlite3`. Будущая история цен будет в `.data/ozon/prices.sqlite3`; файл Randewoo `.data/prices.sqlite3` остаётся отдельным. Парсеры и offline preview вообще не открывают базу. HTTP 200 с JSON не объявляется автоматически подтверждённым подключением аккаунта или проверкой доставки.

Для локального снимка:

```powershell
npm run ozon:network -- --preview
npm run ozon:status
npm run ozon:server-check -- --status
```

Эти команды работают без запросов к Ozon. Первая требует `.secrets/ozon-mcp/capture.json` и сохранённые JSON-ответы рядом с ним. Пример структуры манифеста с искусственным SKU:

```json
{
  "provider": "ozon-capture",
  "version": 1,
  "favorites": {"files": ["favorites-full.network-response"], "limit": 30},
  "cart": "cart-full.network-response",
  "product": {
    "external_id": "123",
    "file": "product-full.network-response",
    "banks": "product-banks.network-response"
  }
}
```

`cart` и `product` необязательны. Файлы ответа ограничены 8 МБ, читаются только из каталога манифеста. Результат явно имеет `live=false`; он не добавляет старые цены в историю как новые наблюдения. Экспорт HAR остаётся запасным способом анализа/импорта; при работающем MCP вручную сохранять HAR не требуется.

## Серверное окружение и следующий этап

Во время первого эксперимента на Ubuntu в отдельный `/var/tmp/price-checker-ozon-spike` загружены Chrome Headless Shell, ffmpeg и распакованные native-библиотеки. Системные пакеты, служба Price Checker, настройки ядра и AppArmor не менялись. Секреты аккаунта туда не копировались.

Браузер запускался от непривилегированного пользователя с включённым sandbox. Запуск завершился до обращения к Ozon: для этого процесса недоступен user namespace. На сервере наблюдался `apparmor_restrict_unprivileged_userns=1`, а `unshare -Ur` от пользователя службы завершился `EPERM`. Причина требует проверки конкретной политики процесса; одного значения sysctl недостаточно для диагноза. Флаги отключения sandbox не применялись.

После согласования следующего эксперимента установлен официальный Google Chrome 155.0.8059.84, Xvfb и необходимые зависимости из пакетного менеджера. В отличие от первого скачанного Chromium, штатный Chrome запускается под уже существующим профилем Ubuntu AppArmor. Настройки ядра и профили AppArmor не изменялись; `--no-sandbox` не использовался. Для renderer через `/proc` подтверждены отдельные user/PID namespaces, `Seccomp=2`, `NoNewPrivs=1` и отсутствие эффективных capabilities. Состояние основного browser-процесса не выдавалось за sandbox renderer.

Chrome запущен от отдельного `ozonbrowser` с приватным профилем в `/var/lib/price-checker-ozon-browser`, виртуальным экраном и лимитом памяти 768 МиБ. Chrome DevTools MCP подключён через временный SSH-туннель; CDP слушал только `127.0.0.1`. После обычного открытия главной Ozon Network показал 403, а страница — предложение выключить VPN/сменить сеть. Авторизация и обход challenge не выполнялись. Пиковая память группы браузера — около 640 МиБ, OOM-kill не было. После проверки браузер, MCP-подключение и туннель остановлены; профиль и приватные доказательства сохранены. Chrome/Xvfb остаются установленными. Продакшен Price Checker не перезапускался.

По отдельному запросу владельца настроены исключения в `/etc/price-checker-proxy/config.json`: `DOMAIN-SUFFIX,ozon.ru,DIRECT`, `DOMAIN-SUFFIX,ozone.ru,DIRECT`, `DOMAIN-SUFFIX,randewoo.ru,DIRECT` перед прежним `MATCH,EOS`. Randewoo уже имел такое исключение. Создана приватная резервная копия конфигурации, кандидат проверен `mihomo -t`, выполнена горячая перезагрузка через локальный controller. Режим `rule`, остальные параметры и выбранный VPN-узел сохранены. Проверены TLS-соединения через HTTP CONNECT и фактические `chains=[DIRECT]` в `/connections` для `www.ozon.ru`, `ir.ozone.ru`, `randewoo.ru`; HTTP-запросы к магазинам при этой проверке не отправлялись.

Mihomo здесь — локальный прокси, TUN и прозрачные порты выключены. В окружении Price Checker через него настроен только Telegram; общих `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` нет. Поэтому прежние Node/Chrome-проверки Ozon уже использовали прямой выход. Добавленные правила закрепляют желаемую маршрутизацию при обращении к Mihomo, но не объясняют исходный 403. Пауза Ozon и расписание не менялись. Правила суффиксов и горячая перезагрузка описаны в официальных [документации правил Mihomo](https://wiki.metacubex.one/en/config/rules/) и [API](https://wiki.metacubex.one/en/api/).

После подтверждения серверного доступа ещё нужны корзина/избранное/обе цены, выбранная доставка, перезапуск и ограниченная проверка по расписанию раз в два часа. Продолжительный тест не запускался и его успешность не заявляется. Локальный MCP используется для исследования. Интервал 2 часа не является гарантией отсутствия ограничений Ozon; ограничения источника имеют приоритет над расписанием. Семантика 403 описана в [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-403-forbidden); точную причину конкретного ответа без дополнительных данных установить нельзя.
